Ansible: Infraestructura como Código y Automatización IT

Gestión de configuración, aprovisionamiento y orquestación agentless para arquitecturas modernas.

1. ¿Qué problema resuelve Ansible?

Desafíos en la gestión tradicional de infraestructura y operaciones IT

Gestión Manual & Error Humano

Configurar servidores individualmente mediante scripts SSH manuales es propenso a equivocaciones, lento e ineficiente a escala.

Configuration Drift (Desviación)

Con el tiempo, los entornos (dev, staging, prod) pierden paridad debido a parches manuales no documentados, generando fallos en producción.

Falta de Repetibilidad

Dificultad para recrear infraestructura destruida o desplegar nuevos nodos idénticos en cuestión de minutos.

Cuellos de Botella Operativos

Los equipos de desarrollo dependen del equipo de SysAdmins/Ops para cada cambio menor o aprovisionamiento de recursos.

2. Explicación de la Herramienta

Naturaleza, licenciamiento y arquitectura interna de Ansible

¿Qué es?

Una plataforma de automatización IT de código abierto para gestión de configuración, despliegue de aplicaciones y aprovisionamiento de infraestructura.

Ecosistema & Soporte

Mantenida por Red Hat (IBM). Amplia comunidad global con Ansible Galaxy (repositorio público de roles y colecciones).

Licenciamiento

Open Source (GPLv3) para Ansible Core/Community. Versión Enterprise: Red Hat Ansible Automation Platform (AAP).

Componentes Principales

Playbooks Archivos YAML que definen el estado deseado mediante tareas declarativas.
Inventory Lista de servidores objetivos (estáticos o dinámicos via AWS/GCP).
Modules Unidades de código en Python ejecutadas en los nodos de destino (apt, yum, docker, copy).
Roles Estructura modular reutilizable que organiza tareas, variables y plantillas Jinja2.
Tasks Acción individual mínima que invoca un módulo con parámetros específicos.
Plugins Extensiones para adaptar ejecución, logs, inventarios dinámicos y conexiones.

2. Flujo Real de Uso en Ansible

Principios de ejecución sin agentes, declarativa e idempotente

01

Arquitectura Agentless

No requiere instalar ningún software cliente ni demonios en los servidores destino. Se conecta utilizando únicamente SSH (Linux/Unix) o WinRM (Windows).

02

Ejecución Declarativa

Tú describes qué estado deseas alcanzar (ej: "Nginx debe estar instalado y corriendo"), no cómo programar los comandos paso a paso.

03

Idempotencia Garantizada

Ejecutar el mismo Playbook 1 o 100 veces produce el mismo resultado exacto. Si el sistema ya está en el estado deseado, Ansible no realiza cambios innecesarios.

3. Casos de Uso Principales

Escenarios reales de aplicación en la industria

1. Gestión de Configuración de Servidores

Estandarización de paquetes, usuarios, llaves SSH, archivos de configuración (p. ej. `/etc/nginx/nginx.conf`) en cientos de instancias simultáneamente.

2. Aprovisionamiento Multicloud

Creación y orquestación de recursos en AWS (EC2, S3), Azure, GCP, DigitalOcean y entornos VMware/vSphere desde una única herramienta.

3. Despliegue de Aplicaciones

Automatización del ciclo de vida de software: clonado de Git, construcción de imágenes Docker, actualización de bases de datos y reinicio de servicios sin downtime.

4. Parches de Seguridad y Cumplimiento

Aplicación automatizada de parches del sistema operativo (Zero-day vulnerabilities) y auditoría contínua de hardening de seguridad (CIS Benchmarks).

4. Integración con el Ecosistema del Curso

Alineación con Configuration Management, Modern DevOps, Containers y GitOps

Configuration Management (CM)

Ansible cubre las 6 áreas funcionales del curso: automatiza Environment Configuration (variables por dev/test/prod), Build & Release Engineering, y garantiza un Deployment trazable y seguro mediante Change Control auditables.

Modern DevOps (IaC & CaC)

Materializa el paso de DevOps Tradicional a Modern DevOps: reemplaza configuraciones manuales por Infrastructure as Code (IaC) y Configuration as Code (CaC), eliminando la automatización hecha a mano.

Contenedores & Cloud-Native

Resuelve la "Matrix of Hell" provisionando automáticamente nodos Linux/Docker runtime, preparando el entorno para orquestadores como Kubernetes y acelerando pipelines CI/CD.

GitOps & Source Code Management

Los Playbooks viven en Git como la **única fuente de verdad** (SCM). Cada modificación se versiona (`git commit`/`push`), permitiendo ejecuciones automatizadas y rollback auditables.

Artefactos Producidos y Consumidos en el Pipeline

Artefactos Consumidos (Inputs):
  • Código fuente / Playbooks YAML en Git
  • Inventarios estáticos/dinámicos (Cloud API)
  • Variables de entorno & Secretos (Ansible Vault)
Artefactos Producidos (Outputs):
  • Infraestructura estandarizada e immutable
  • Reportes de auditoría y paridad de entorno
  • Logs de ejecución (OK / Changed / Failed)

6. Ejemplo Práctico Mínimo

Estructura de Proyecto y Playbook para Despliegue y Configuración de Servidor Web Nginx

Estructura del Proyecto & Inventario (`hosts.ini`) 
Ansible_Demo/
├── inventory/
│   └── hosts.ini
├── templates/
│   └── index.html.j2
├── playbook.yml
└── README.md

# inventory/hosts.ini
[webservers]
# Modo Local (demo en vivo en WSL/Linux):
localhost ansible_connection=local

# Modo Remoto (SSH agentless en producción):
# server1 ansible_host=192.168.1.50 ansible_user=ubuntu
Playbook Principal (`playbook.yml`) 
---
- name: Despliegue y Configuración de Nginx
  hosts: webservers
  become: true

  vars:
    app_version: "1.0.0"

  tasks:
    - name: 1. Instalar servidor Nginx
      apt:
        name: nginx
        state: present
        update_cache: true

    - name: 2. Desplegar plantilla Jinja2
      template:
        src: templates/index.html.j2
        dest: /var/www/html/index.html
        mode: '0644'
      notify: Reiniciar Nginx

    - name: 3. Asegurar servicio activo
      service:
        name: nginx
        state: started
        enabled: true

  handlers:
    - name: Reiniciar Nginx
      service:
        name: nginx
        state: restarted

7. Paso a Paso para Ejecución

Comandos y secuencia de verificación en terminal

Paso 1: Probar Conectividad (Ping SSH)

Verifica que Ansible pueda conectarse al servidor remoto antes de ejecutar tareas.

ansible webservers -i inventory/hosts.ini -m ping
Paso 2: Simulación de Cambios (Dry-Run / Check Mode)

Evalúa qué cambios se realizarían sin modificar realmente el servidor.

ansible-playbook -i inventory/hosts.ini playbook.yml --check
Paso 3: Ejecución Real del Playbook

Aplica el estado deseado: instala Nginx, renderiza la plantilla HTML y activa el servicio.

ansible-playbook -i inventory/hosts.ini playbook.yml
Paso 4 (En Vivo): Idempotencia y Autocuración (Self-Healing)

Reejecutar para comprobar Idempotencia (changed=0) o simular caída con sudo service nginx stop para ver cómo Ansible repara el error humano automáticamente.

9. Ventajas y Desventajas (Análisis Matricial)

Evaluación técnica integral para adopción empresarial

Ventajas Clave

  • Costo: Gratuito y Open Source en su versión Core.
  • Sin Agentes: Menos consumo de memoria y CPU en nodos remotos; no hay agentes para actualizar.
  • Curva de Aprendizaje: Sintaxis YAML limpia e intuitiva para SysAdmins y Devs.
  • Comunidad: Enorme biblioteca de roles listos en Ansible Galaxy.
  • Seguridad: Usa autenticación SSH existente y cifrado via Ansible Vault.

Desventajas & Limitaciones

  • Velocidad de Ejecución: Puede ser más lento que soluciones basadas en agentes (p. ej. SaltStack) en miles de nodos.
  • Gestión de Estado: No guarda un archivo de estado global centralizado como Terraform (`.tfstate`).
  • Complejidad YAML: Tabulaciones e identación estrictas pueden causar errores sutiles de sintaxis.

10. Buenas Prácticas

Recomendaciones para mantener código limpio y seguro

Uso de Ansible Vault

Cifrar siempre contraseñas, tokens y llaves privadas dentro del repositorio Git.

Estructura Modular (Roles)

Dividir Playbooks grandes en Roles independientes (tasks, handlers, vars, templates).

Testing & Dry-Run

Probar Playbooks usando `--check` y herramientas como Molecule y ansible-lint antes de aplicar en producción.

11. Riesgos y Errores Comunes

Trampas operativas y cómo evitarlas

Sensibilidad a Indentación en YAML

Un espacio adicional o mal alineado provocará fallos crípticos durante el parsing.

Uso Excesivo de Módulos Shell/Command

Ejecutar comandos Bash directamente rompe la idempotencia. Debe preferirse el uso de módulos nativos.

Timeouts y Timeouts SSH

En redes de alta latencia o despliegues masivos, las conexiones SSH no optimizadas pueden expirar prematuramente.

Hardcoding de Variables

Escribir direcciones IP o credenciales directamente en los Playbooks en lugar de usar variables o inventarios dinámicos.

12. Conclusiones y Criterio Profesional

¿Cuándo sí y cuándo no usar Ansible?

¿Cuándo SÍ usarlo?

Para automatizar la configuración interna de OS, orquestar despliegues híbridos, estandarizar servidores existentes y proyectos que requieren despliegue rápido sin infraestructura compleja de gestión.

¿Cuándo NO usarlo?

Para aprovisionar pura infraestructura en la nube desde cero (Terraform es mejor para esto) o en sistemas 100% serverless sin servidores ni OS que administrar.
